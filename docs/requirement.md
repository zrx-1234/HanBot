HanBot需求文档（细化版）

    本文档在orig_requirement.md的基础上细化。已确定的决策：
    1. 使用者只有一人，不做多用户、注册、租户相关的任何功能。
    2. 第一阶段只做网页端，Android APP放到后面的阶段。
    3. 自我进化采用"它提议、我批准"的方式，HanBot不擅自修改自己的记忆。
    4. 部署在一台有公网IP的Linux ECS服务器上，需要考虑基本的安全防护。

一、核心概念

    系统里有两个容易混淆的东西，先定义清楚：

    1. 会话：用户和HanBot的一段对话载体，长期存在，用户可创建、可删除。一个会话里可以先后产生多个任务。
    2. 任务：一次具体的Agent执行，有开始有结束。用户发出一条需要执行的指令，就产生一个任务。任务有以下状态：
    （1）排队：已接受，尚未开始执行
    （2）运行中：正在执行
    （3）等确认：Agent停下来，等用户回答问题或批准操作
    （4）已完成
    （5）已中断：被用户手动停止
    （6）失败：执行出错
    原需求中的状态灯对应关系：蓝灯-运行中（含排队），黄灯-等确认，绿灯-已完成，红灯-中断或失败。等确认是一种特殊的暂停态，必须和运行中区分显示，否则用户分不清"它在干活"还是"它在等我"。

    3. 能力：HanBot可执行的一种技能或工具，形态包括技能文档（Skill）和工具服务（MCP Server）两种。能力装好后不等于生效，还需要激活。
    4. 记忆：HanBot在交互中积累的、对用户和自身经验的总结，持久化为文档，详细见后端功能第4条。

二、网页端交互功能

    1. 登录。服务器有公网IP，必须登录后才能使用。单用户，用户名密码即可。连续登录失败限次锁定一段时间。全程HTTPS。
    2. 聊天界面。每个会话一个聊天窗口，支持发送文字和图片，能展示Agent的执行过程（当前在做什么、调用了什么工具）。
    用户发出的消息不区分"聊天"和"任务"：如果只是问答闲聊，不生成任务；一旦Agent判断需要执行操作（调工具、跑脚本、写文件），就生成任务并显示状态灯。
    3. 会话列表与任务列表。可新建会话、删除会话（删除时连带其目录，需二次确认）。会话点进去能看到其中所有任务及状态灯。运行中的任务用户可手动强行停止。
    4. 任务详情与时间线。每个任务保存完整的行动轨迹：每一步思考、每次工具调用及其参数和结果、每次文件写入、每次模型切换。以时间线形式展示，可逐条展开。用户可以回看任何历史任务的完整过程。
    5. 确认交互。Agent需要用户参与时，在聊天界面内弹出确认卡片，卡片上直接给出选项按钮或输入框，用户不用打字也能一键批准、否决或补充说明。任务停在等确认状态，用户回答后继续执行。
    6. 提醒。分三级：
    （1）阻塞级：任务停在等确认，不回答就不动。网页在线时界面内提醒（角标加声音），网页不在线时浏览器通知，浏览器通知不可达时发邮件兜底。
    （2）知会级：任务完成待验收、任务失败、任务超时，发一次通知即可。
    （3）静默级：普通进度更新，只写入时间线，不打扰。
    7. LLM API源配置。支持OpenAI和Anthropic两种接口格式。每个源配置：名称、接口格式、地址、密钥、可用模型列表、优先级。提供连通性测试按钮。可设全局默认模型，也可临时按会话指定。
    8. 全局设置。系统提示词、回答风格、以及执行相关的开关（如任务超时时长上限）。
    9. 能力市场。第一阶段先做本地安装：用户把能力文件放到服务器指定目录，或填一个GitHub地址由HanBot拉取。每个能力有名称、说明、激活开关。激活分两级：全局激活（所有会话可用）和会话内手动激活（默认不加载，用的时候再开）。能力格式直接兼容SKILL.md规范和MCP服务器协议，不自造格式，社区的现有生态可以直接用。
    10. 记忆面板。展示HanBot对用户的全部认知：偏好、习惯、经验教训、办事流程。每条记忆可查看原文、编辑、删除。HanBot新提议的记忆进入"待批准"区，用户批准后生效，不批准不生效。这个面板是用户检查和纠正HanBot认知的地方。
    11. 成本看板。每个任务记录token消耗和估算费用。可按日、按模型、按任务汇总查看。自托管的意义之一就是账单透明。
    12. 存储占用显示。显示总配额和当前已用，接近上限时提醒。

三、后端功能

    1. LLM API源容灾。切换分两种情形，区别对待：
    （1）新任务开始时：按用户排的优先级和当前可用性选择源，随便切。
    （2）任务运行中：只有当前源彻底不可用（连续报错、额度用尽、断连）才降级切换，且在步骤边界进行（一次工具调用结束、下一次请求发出之前），不在半截思考中切换。
    每次切换记录到任务时间线。每个任务在时间线和详情里标明本次实际用了哪个源哪个模型。
    2. 文件系统管理。服务器端设总容量上限，可配置。每个会话新开一个目录，存放对话记录、任务运行数据（脚本、数据文件）、产出文件。产出文件在网页端可浏览和下载。会话删除时目录一并删除。
    3. 运行沙箱。每个任务在独立的Docker容器中执行，容器内只能访问本会话目录，不能碰系统其他路径。容器限制CPU、内存和最长执行时长，超时自动停止并通知用户。网络访问默认放开，可配置黑名单。
    另外，沙箱内不存放任何API密钥：需要密钥的对外调用（如调用外部服务）由后端代理执行，容器里的程序接触不到密钥。
    4. 自我进化。分两个角色：
    （1）主Agent：在线执行任务。运行时按相关性检索已有记忆，把相关的部分注入本次上下文。系统提示词只放固定的核心内容（人格、安全边界、最根本的几条偏好），不放全部记忆，避免无限膨胀。
    （2）记忆Agent：在服务器闲时定期复盘最近的会话和任务，产出提议：新的用户偏好、经验教训、可复用的办事流程。所有提议只进"待批准"区，用户批准后才写入生效。用户也可以手动直接添加记忆。
    记忆分四层：核心层（人格与边界，基本固定）、用户画像、经验教训、会话摘要归档。第一阶段的检索用关键词加元数据即可，跑起来后再考虑向量检索。
    5. 任务队列。同一时刻最多运行N个任务（可配置），超出的排队。单机资源有限，避免并发把服务器打满。

四、安全与运维

    1. HTTPS，登录，失败限次。
    2. API密钥加密存储，接口返回时不回显完整密钥。
    3. Agent的一切执行限制在沙箱内（见后端功能第3条）。
    4. 数据备份：数据库和会话目录定期打包，用户可在网页端下载备份包。单机部署没有别人帮你兜底，备份是硬需求。
    5. 服务日志留存，出问题时能查。

五、分阶段计划

    Phase 1：跑通核心闭环
    登录、聊天界面、会话与任务（含状态灯与强停）、确认卡片、任务时间线、单LLM源接入、Docker沙箱、每会话独立目录与配额、网页提醒（阻塞级）。
    这一期结束时能完整跑一次"下指令、执行、等确认、完成"的流程。

    Phase 2：记忆与容灾
    记忆Agent与待批准流程、记忆面板、多LLM源容灾切换、成本看板、邮件提醒兜底、能力本地安装与激活开关。

    Phase 3：生态与扩展
    能力市场完善（远程安装）、定时任务与条件触发（如每天早上八点的晨报）、多模态接入（视觉理解等做成工具调用）、Android APP（原生通知栏可直接批准确认卡片）。

    暂不做：
    多用户、语音输入输出、Agent自主修改记忆（始终保持它提议我批准）、开放注册类的能力市场（只有自己用，不需要平台化）。

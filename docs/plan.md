HanBot开发计划

    本计划对应requirement.md与design.md。前提：代码全程由AI编写，因此排期不按人力工时，按"开发会话"计。一个开发会话指一次完整的AI工作往返：拿到目标、写代码、跑测试、提交。AI写代码的速度不是瓶颈，真正的瓶颈是三件事：等资源（域名、服务器、API Key）、真模型真机验收、用户拍板。所以本计划把用户侧动作全部显式标出，并对齐说明：凡是依赖用户资源的步骤，都安排了不被它卡住的并行路径。

一、开发方式

    1. 开发环境：开发机是Windows，生产是Linux，因此从一开始就一切跑在Docker里，本地与生产用同一套compose，避免环境漂移。Windows裸机上不装Python依赖、不直接跑后端。
    2. 仓库纪律：git单main分支，小步提交，每个会话结束时必须测试全绿才允许提交。每会话在docs/DEVLOG.md追加一段（做了什么、改了哪些决策、遗留什么），下次会话AI先读CLAUDE.md和DEVLOG再动手——这是对抗AI上下文丢失的主要手段。
    3. 质量靠自动化，不靠人肉review：后端pytest（重点覆盖LLM网关格式互转、任务状态机、沙箱管理器三条命脉）+ ruff + mypy；前端tsc + vite build全绿。验收标准写死在每个里程碑里，机器可验证的用机器验，体验类的由用户在真实环境过一遍。
    4. 范围纪律：一个会话只做一个里程碑内的事。Phase 2/3的功能不在Phase 1代码里"顺手预留"，想加的东西记进DEVLOG的"将来"栏，不直接写代码。
    5. 依赖版本全部锁定（requirements.txt、package.json、pubspec.yaml），防止AI幻觉出不存在的API或用了已废弃的写法；引入任何新依赖前先查证再用。

二、开工准备（双方并行）

    用户侧（不阻塞本地开发，但M1.5上生产前必须就绪）：
    1. 买域名，做好DNS解析到ECS公网IP。
    2. ECS开通：2核4G、40G系统盘起，Ubuntu 22.04或Debian 12，SSH密钥登录。
    3. 至少一个LLM API Key（OpenAI或Anthropic格式任一）。
    4. 开发机装好Docker Desktop和git。

    AI侧（用户资源没到位时先做这些，不空等）：
    1. git仓库初始化，目录结构按design.md第三节落地。
    2. 写CLAUDE.md：项目约定、常用命令（起服务、跑测试、迁移）、禁区（不许改docs/orig_requirement.md、不许跳过测试提交）。
    3. compose骨架能空跑起来。
    完成标志：本地docker compose up能起一个空壳服务。

三、Phase 1里程碑（对应design.md第十七节M1至M8）

    排序原则：先搭能部署的骨架，再搭能跑Agent的骨架，再上安全（沙箱），最后闭环交互和系统管理。本地开发全程用http，不受域名影响。

    M1 部署底座（预计1至2会话）
    做什么：compose（backend+caddy+空ntfy位）、登录（argon2id+cookie+失败锁定）、Caddyfile。
    验收：本地浏览器http://localhost能登录、能锁定、能解锁。
    用户侧：无。可与M2并行等待域名。

    M1.5 上生产（预计1会话加用户半天）
    做什么：ECS初始化脚本（ufw、SSH加固、装docker）、deploy/README部署文档、Caddy真域名HTTPS。
    验收：手机浏览器通过https域名登录成功。
    用户侧：提供域名、DNS、ECS；按文档执行部署（AI全程陪同）。
    时机：域名一到随时插入，最晚不迟于M4（之后的验收都应在生产形态下做）。

    M2 配置底座（预计1至2会话）
    做什么：全部建表+alembic、settings与sources的CRUD及连通性测试按钮、密钥AES加密落库。
    验收：界面配好一个真实API源，测试按钮返回成功。
    用户侧：提供API Key。从M2起所有里程碑的验收都在ECS上做。

    M3 Agent循环v1（预计2至3会话）
    做什么：LLM网关+第一个适配器（先接用户手头有的那种格式，另一种Phase 2补）、聊天流式、messages与usage_log落库、http_request工具。此阶段还没有沙箱，无bash。
    验收：能流式问答；能完成"用http_request查一个公开API然后总结"。
    用户侧：验收时留意回答质量与速度是否符合预期。
    决策点：无。

    M4 沙箱与任务态（预计2至3会话）
    做什么：hanbot-sandbox镜像、容器生命周期管理、bash/read/write/list四件套、任务懒创建、状态机、强停、时间线落库。
    验收：让它"写个脚本统计workspace里的数据文件"，全程时间线可回看；强停后时间线完整。
    用户侧：观察ECS资源占用（内存、磁盘），确认配额默认值合不合理。

    M5 确认闭环（预计2会话）
    做什么：ask_user工具、确认卡片、任务挂起与答复续跑、WS推送、浏览器通知（阻塞级）。
    验收：完整跑一次"下指令、执行、等确认、答复、完成"；页面关掉再打开能接上状态。
    用户侧：这是产品灵魂时刻，认真体验，把不顺手的地方全列出来。

    M6 界面完善（预计1至2会话）
    做什么：会话管理（新建、删除含目录、二次确认）、任务列表与状态灯、时间线交互打磨、transcript.md导出追加。
    验收：日常使用无卡壳；删除会话后磁盘同步消失。
    用户侧：连续用两三天真实任务，攒反馈。

    M7 系统管理（预计1会话）
    做什么：存储配额统计与展示、backup.sh+VACUUM INTO、备份页面（列表、手动触发、下载）、登录日志。
    验收：手动备份出包、下载、按文档演练一次恢复成功。
    用户侧：确认恢复演练真的做了（不是看了文档就算）。

    M8 收尾上线（预计1至2会话）
    做什么：结构化日志滚动、异常路径补齐（超时、断连、后端重启恢复）、安全清单逐项过（design.md第十五节）、DEVLOG整理进docs。
    验收：安全清单全过；杀掉后端进程重启，running任务正确转failed、awaiting任务仍可答复。
    用户侧：宣布Phase 1验收通过，开始真实日常使用。

    Phase 1合计约12至17个开发会话。若用户侧资源与验收及时跟上，墙钟约三到四周；被资源卡住时，本地进度可推进到M4再等。

四、Phase 2功能块（顺序即依赖）

    P2-1 多源容灾（1至2会话）：第二适配器、降级与冷却、model_switch入时间线。验收：人为把首选源密钥改错，任务在步骤边界自动切换并继续完成。
    P2-2 ntfy通道（1会话）：自建ntfy、Caddy反代、去重逻辑。验收：关掉浏览器，触发等确认，手机ntfy收到高优先级通知。
    P2-3 能力安装（2会话）：SKILL.md解析、zip上传与GitHub拉取、索引注入、两级激活。验收：装一个社区技能，Agent按索引自行读全文并用对方法。
    P2-4 记忆系统（3至4会话，Phase 2核心）：记忆Agent与每日复盘、待批准流、记忆面板、注入检索（关键词版）、digest摘要。
    验收分三步：①复盘跑一晚产出结构正确的提议；②批准后下个任务确实被该记忆影响（时间线可见注入）；③面板改一条记忆立即生效。
    P2-5 成本看板（1会话）：日/模型/任务三视图、每日费用软闸通知。验收：数字与usage_log对得上。
    Phase 2合计约8至11个开发会话。此阶段起每个功能块配pytest，记忆系统额外配几条端到端用例。

五、Phase 3功能块

    P3-1 定时任务（1至2会话）：无会话触发的任务、用户配置界面、晨报类模板。这是Agent从被动变主动的第一步，放最前。
    P3-2 Flutter基础版（3至4会话）：登录（长期token）、会话列表、聊天+任务卡片、时间线、强停与确认答复。验收：手机上完整走一遍M5场景。
    P3-3 通知与通知栏操作（1至2会话）：内置ntfy长轮询订阅、通知栏批准/拒绝按钮（直调task_reply）。过渡方案同步提供：官方ntfy APP订阅自家服务器的配置说明。
    P3-4 MCP接入（2会话）：后端MCP client、外部server以独立容器运行、工具并入注册表与激活开关。
    P3-5 多模态（1至2会话）：图片作为消息附件、视觉理解作为后端面工具。
    P3-6 能力市场完善（1会话）：远程一键安装。
    Phase 3合计约9至13个开发会话。

六、用户决策点汇总（到时需要拍板）

    1. M2：先接哪种API格式（取决于手头Key）。
    2. M4后：沙箱内存、CPU、并发上限默认值是否按实测调整。
    3. P2-4运行两周后：复盘频率与注入预算是否调整；记忆质量不理想时调提示词还是调策略。
    4. P3-2前：APP是否需要平板适配（影响少量布局工作）。
    5. 随时：DEVLOG"将来"栏里攒的念头，Phase间统一裁决是否采纳。

七、风险与对策

    1. AI幻觉出错误API或过时写法：锁版本；新依赖先写最小验证脚本跑通再进代码；测试覆盖三条命脉（网关互转、状态机、沙箱）。
    2. 跨会话上下文丢失：CLAUDE.md+DEVLOG制度；重要决策必须落到docs/文档，不许只存在于会话里。
    3. AI大面积重构冲动：纪律写进CLAUDE.md——不许在没有失败测试的情况下重构；里程碑内只做里程碑的事。
    4. Windows与Linux差异：一切经Docker；生产镜像只在Linux构建；M1.5后验收全部在ECS做，本地差异问题在早期暴露。
    5. 用户侧资源延迟：本地路径已排到M4不依赖域名；API Key没有前，M3可用任意一家免费测试端点先打通管道，Key到位后立刻真实验收。
    6. 集成问题集中在M4与M5（Docker内跑Docker、WS长连接、挂起恢复）：这两段预留的会话数最多，属于已知难点，不视为延期。

八、总账

    Phase 1：12至17会话，墙钟三到四周（取决于资源与验收节奏）。
    Phase 2：8至11会话，墙钟约两周。
    Phase 3：9至13会话，墙钟约两到三周。
    全程合计约30至40个开发会话。计划里的会话数是"工作量"的诚实估计，墙钟时间是"用户侧不成为瓶颈"的理想值；每完成一个里程碑，按实际速度修订一次本计划的后半段。
